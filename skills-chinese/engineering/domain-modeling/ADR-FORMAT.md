# ADR 格式

ADR 存放在 `docs/adr/` 中，并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

延迟创建 `docs/adr/` 目录：仅在需要第一个 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么、我们决定了什么，以及为什么。}
```

仅此而已。一个 ADR 可以只有一段话。其价值在于记录做出了一项决策*以及*背后的原因，而不是填满各个小节。

## 可选小节

仅在能带来真正价值时才包含这些小节。大多数 ADR 并不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在重新审视决策时很有用
- **Considered Options**（已考虑的方案）：仅在被否决的备选方案值得记住时包含
- **Consequences**（影响后果）：仅在需要指出不明显的下游影响时包含

## 编号

扫描 `docs/adr/` 查找已存在的最大编号，并在此基础上加一。

## 何时提议创建 ADR

必须满足以下全部三点：

1. **难以逆转**：后续改变主意的代价很大
2. **脱离上下文会令人费解**：未来的读者看到代码时会疑惑“究竟为什么他们要这样做？”
3. **真实权衡的结果**：存在真正的备选方案，且出于特定原因选择了其中之一

如果一个决策很容易逆转，请跳过它：你随时可以撤销它。如果不令人费解，没有人会追问为什么。如果没有真正的备选方案，除了“我们做了显而易见的事情”之外，没有什么值得记录的。

### 符合条件的内容

- **架构形态。** “我们使用 monorepo 单体仓库。” “写入模型采用事件溯源，读取模型投影到 Postgres 中。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过领域事件通信，而非同步 HTTP 调用。”
- **具有锁定效应的技术选型。** 数据库、消息总线、身份认证提供商、部署目标平台。并非每个库都需要：仅记录那些需要耗费一个季度才能替换掉的选型。
- **边界与范围决策。** “客户数据归 Customer 上下文所有；其他上下文仅通过 ID 引用。” 明确说“不”与说“是”具有同等价值。
- **特意偏离显而易见的常规方案。** “由于 X 原因，我们使用手写 SQL 而非 ORM。” 任何合理的读者可能会做出相反假设的决策。这能防止下一位工程师去“修复”那些特意而为的设计。
- **代码中不可见的约束。** “由于合规要求，我们无法使用 AWS。” “由于合作伙伴 API 契约，响应时间必须在 200 毫秒以内。”
- **被否决的备选方案（当否决原因并不显而易见时）。** 如果你考虑过 GraphQL 但出于微妙原因选择了 REST，请将其记录下来；否则六个月后会有人再次提议使用 GraphQL。
