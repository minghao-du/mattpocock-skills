# 领域建模 (Domain Modeling)

在设计时积极构建并提炼项目的领域模型。这是一门*主动*的学科：质疑术语、设计边缘用例场景，并在词汇和决策明确成型的瞬间将其记录下来。（仅仅为了获取词汇而*阅读* `GLOSSARY.md` 并不是这项技能：那是任何技能都可以做到的一行习惯。这项技能适用于你正在修改模型，而不仅仅是使用它的时候。）

## 文件结构

大多数代码库只有一个单一上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `GLOSSARY-MAP.md`，则代码库包含多个上下文。该映射指明了每个上下文所在的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

延迟创建文件：仅在有内容要写时才创建。如果不存在 `GLOSSARY.md`，在确定第一个术语时创建它。如果不存在 `docs/adr/`，在需要第一个 ADR 时创建它。

## 会话期间

### 对照词汇表提出质疑

当用户使用的术语与 `GLOSSARY.md` 中现有的表述冲突时，立即指出：“你的词汇表将‘取消’定义为 X，但你的意思似乎是 Y。到底是哪一个？”

### 提炼模糊语言

当用户使用含糊不清或被重载的术语时，提出一个精确的标准术语：“你说的是‘账户’：你指的是 Customer（客户）还是 User（用户）？这是两码事。”

### 讨论具体场景

在讨论领域关系时，用具体场景对其进行压力测试。设计能够探究边缘用例的场景，迫使用户对概念之间的边界给出精确界定。

### 与代码交叉核对

当用户说明某项功能的工作方式时，检查代码是否一致。如果发现矛盾，将其指出：“你的代码取消了整个订单（Order），但你刚才说可以部分取消。哪一个是正确的？”

### 直接就地更新 GLOSSARY.md

当一个术语确定下来时，立即就地更新 `GLOSSARY.md`。不要批量处理：在它们发生时即刻捕获。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 应当完全不含任何实现细节。切勿将 `GLOSSARY.md` 视为规格说明、草稿纸或实现决策的存放处。它只是一个词汇表，仅此而已。

### 谨慎提议创建 ADR

仅在满足以下全部三点时才提议创建 ADR：

1. **难以逆转**：后续改变主意的代价很大
2. **脱离上下文会令人费解**：未来的读者会疑惑“他们究竟为什么这样做？”
3. **真实权衡的结果**：存在真正的替代方案，且出于特定原因选择了其中之一

如果缺少这三点中的任何一点，请跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
